# 1. 개요 · 배경

## 1.1 무엇을 하는 서비스인가

기업(제휴 거래처)이 임직원 경조사에 보낼 화환·화분·난을 주문하고, 사용한
금액을 **월 후불로 정산**하는 B2B 서비스입니다. 여기에 개인 고객이 네이버
스토어·카카오톡 채널 등으로 넣는 **B2C 주문**이 같은 배송 인프라를 씁니다.

- **거래처 포털** (`#/app/*`) — 6개 화면. 거래처 담당자가 직접 주문하고
  주문 내역·거래명세서·정산 현황을 조회합니다.
- **관리자 콘솔** (`#/admin/*`) — 7개 화면. 주문 처리, 거래처 관리, 정산,
  단가, 담당자 계정을 다룹니다.

## 1.2 왜 구 시스템을 대체하는가

구 시스템은 관리자 화면 11개로 이뤄진 **내부 전용 도구**였습니다. 거래처는
전화·카카오톡으로 주문을 넣고, 관리자가 대신 등록하는 구조였습니다. 신규
시스템의 핵심 변화는 **거래처가 직접 주문하는 포털의 신설**이며, 그에 따라
정산·명세서·단가가 거래처에게 공개됩니다.

## 1.3 이번 이관에서 확인된 사실

구 시스템에 직접 접속해 데이터를 대조한 결과(2026-09-15), 문서로만 알던
것과 다른 점이 두 가지 드러났습니다. 설계에 직접 영향을 줍니다.

**① 지역 규칙은 배송비 할증이 아니라 「반입 가능 상품 허용 목록」이다.**
구 `지역별 반입 리스트(503)` 25건 중 23건이 "이 지역·이 장례식장에서는
*이 상품만* 반입 가능" 형태이고, 배송 불가는 전남 신안·충남 계룡 2곳입니다.
신규가 갖고 있던 배송비 할증 13건과는 지역이 거의 겹치지 않아 **대체가
아니라 병존**해야 합니다. (→ 5.6, 10.1)

**② 「거래처 참고사항」은 메모가 아니라 거래 조건이다.**
예: (주)홈팩 — "상품금액 75,000원으로 기재, 무조건 특대상품 발송 / 추가
배송비·취소비용 개별청구 / 배송완료 이미지 전달 필수". 19개 거래처 중
12곳이 이런 조건을 갖고 있으며, 누락되면 주문마다 사고가 납니다.
주문 처리 화면에서 담당자에게 반드시 노출해야 합니다. (→ 4.3)

## 1.4 이관 범위

| 대상 | 건수 | 결정 |
|---|---|---|
| 거래처 | 23 → **19** | 이관. 꽃집(협력 화원) 3곳과 테스트 레코드 1건 제외 |
| 사용자 계정 | 7 → **3** | 최근 1년 내 로그인 계정만. 비밀번호는 이관하지 않음 |
| 지역별 반입 규칙 | **25** | 전량 이관 + 기존 배송비 규칙 13건과 통합 |
| 주문 | 5,639 | **폐기** |
| 하트리 사전예약 설문 | 174 | **폐기** (개인정보 포함 — 파기 절차 필요) |
| 계약체결 영업 정보 | 25 | **폐기** (필드는 신설하되 값은 옮기지 않음) |

구 시스템이 정본입니다. 신규에 있던 데모 거래처 데이터는 전량 교체됐습니다.

## 1.5 이 문서가 다루지 않는 것

- 협력 화원(꽃집) 발주·지급 정산 — 이번 범위 밖 (→ 10.3)
- 모바일 — 웹 반응형은 하지 않고 **별도 모바일 앱 연동**을 추후 작업(상세 미정 → 10.4 Q8)
- 결제 수단 관리 — 외부 채널 정산으로 처리 (→ 10.3)
- 프런트엔드 구현 상세 — 코드와 `CLAUDE.md` 참조

# 2. PRD (제품 요구사항)

## 2.1 문제 정의

| # | 문제 | 현상 |
|---|---|---|
| P1 | 주문 접수가 사람을 거친다 | 거래처가 전화·카톡으로 주문 → 관리자가 수기 등록. 오전에 몰리면 누락·오타 |
| P2 | 정산 근거를 설명하는 데 시간이 든다 | 온라인장부 → 카카오톡 안내 → 바로빌 발행을 사람이 이어붙임 |
| P3 | 거래 조건이 담당자 머릿속에 있다 | "이 거래처는 무조건 특대" 같은 규칙이 자유 메모에만 존재 |
| P4 | 지역 반입 제한을 주문 후에 발견한다 | 접수 후 화원이 거절 → 재작업·사과 |
| P5 | 누가 무엇을 바꿨는지 남지 않는다 | 금액이 걸린 동작(정산·단가)에 이력 없음 |

## 2.2 사용자

| 역할 | 설명 | 주 사용 화면 |
|---|---|---|
| **거래처 담당자** | 제휴기업의 총무·인사 담당. 경조사 발생 시 주문 | 포털 6개 |
| **정산·회계 담당자** | 거래처 내 계산서·입금 담당. 1명 지정 | 포털 정산·명세서 |
| **운영 담당자** | 주문을 받아 화원에 발주하고 배송을 확인 | 관리자 주문·대쉬보드 |
| **최고관리자** | 거래처 승인, 단가 결정, 정산 마감 | 관리자 전체 |

## 2.3 목표 · 비목표

**목표**
1. 거래처가 **3분 안에** 주문을 마칠 수 있다 (4단계 위저드).
2. 운영 담당자가 **한 화면에서** 오늘 할 일을 파악한다 (대쉬보드).
3. 정산이 **사람의 이어붙이기 없이** 명세서 발급 → 동의 → 계산서 → 입금
   확인까지 흐른다.
4. 거래 조건·지역 제한이 **주문 시점에** 드러난다.

**비목표**
- 화원(공급자) 측 발주·정산 관리 — 별도 시스템
- 경조사 자체의 일정 관리(달력·리마인더)
- 재고 관리

## 2.4 성공 기준

| 지표 | 현재(구 시스템) | 목표 |
|---|---|---|
| 거래처 주문 중 포털 접수 비율 | 0% | 3개월 내 70% |
| 주문 → 발주 처리 소요 | 측정 없음 | 접수대기 평균 30분 이내 |
| 마감 전 수동 동의율 (자동 동의 제외) | 측정 없음 | 90% |
| 반입 제한으로 인한 재작업 | 측정 없음 | 월 0건 |

## 2.5 제약

- **결제는 후불이다.** 주문 시점에 결제가 일어나지 않습니다. 따라서 주문
  확정과 대금 회수가 분리되며, 거래처 신용이 곧 리스크입니다.
- **배송은 당일이 기본이다.** 접수 시각이 배송 가능 여부를 좌우합니다
  (영업시간 09:00~18:30).
- **화환은 반품이 없다.** 취소는 제작 착수 여부에 따라 수수료가 갈립니다.

# 3. 유저 플로우

각 플로우는 **정상 경로 → 예외 경로** 순으로 적었습니다. 예외 처리가 빠지면
운영이 각자 판단하게 되므로 예외를 먼저 확정해야 합니다.

## 3.1 제휴기업 가입 → 승인

```
[거래처]                                   [관리자]
1단계 계정 설정 (아이디·비밀번호)
2단계 담당자 정보 (이름·부서·연락처)
3단계 사업자 정보 + 사업자등록증 첨부 + **이용약관 동의**(자동 동의 조항 포함)
   └─ 첨부 없으면 진행 불가 · 약관 동의 없으면 진행 불가 (`terms_agreed_at`·`terms_version` 기록)
   └─ 이관 거래처 19곳은 가입 절차가 없었으므로 **첫 로그인에서 게이트 다이얼로그**로 한 번 받는다.
      약관 버전이 오르면 다시 받는다(2026-09-17 결정)
        │
        ├──► 거래처 상태 "승인대기" 로 생성
        │     유입 경로 = "셀프 가입" 자동 기록
        │                                  거래처 목록 › 승인대기 탭
        │                                  상세 열어 등록증 확인
        │                                     ├─ 승인 → 상태 "활성"
        │                                     └─ 거부 → 상태 "반려" + 사유 필수
        ▼
   승인 전에는 로그인할 수 없다 — 로그인 화면이 상태별 안내(→ 6.2, 2026-09-25 결정)
```

**예외**
| 상황 | 처리 |
|---|---|
| 사업자번호가 이미 등록됨 | 막지 않는다. 같은 법인의 **부서 분리**가 정상 시나리오다(법무법인 세종 2건). 부서 입력을 필수로 올리고 안내만 띄운다 |
| 거부 후 재신청 | 같은 아이디로 재가입 시 반려 사유를 보여주고 수정 제출. ⚠ 서버 필요 |
| 승인 후 사업자 폐업 | 상태 "정지". 기존 주문·정산은 남는다. 정지·반려 거래처는 로그인할 수 없다(→ 6.2) |
| 등록증과 입력값 불일치 | 거부 사유 코드 `증빙 불일치` (→ 4.2) |

## 3.2 주문 접수 (거래처 포털 4단계)

```
1단계  경조사 선택(근조/축하) → 부고장·청첩장 링크 붙여넣기(선택)
       └─ 링크 파싱 성공 시 배송지·일시 자동 입력 (→ 9.3.1)
          ※ 관리자 등록 모달에만 있는 '텍스트 인식'(→ 9.3.2)은 여기에 없다
       → 상품 선택 (거래처 적용 단가로 표시)
2단계  배송지 입력
       ├─ 주소검색(우편번호) 또는 직접 입력
       ├─ 지역 규칙 판정 ─┬─ 배송불가 → 진행 차단
       │                  ├─ 반입 제한 → 허용 상품 안내, 불일치 시 진행 차단
       │                  └─ 추가 배송비 → 금액 안내
       → 받는분·배송일시(날짜·시간 지정 / 즉시배송)
3단계  리본문구 · 보내는분(발송인 프로필에서 선택 가능)
4단계  확인 → 배송완료 알림 수신자 확인 → 접수
```

**배송완료 알림 수신자**는 4단계에서 한 명단으로 보여줍니다.

| 구분 | 출처 | 기본값 |
|---|---|---|
| 받는분 | 2단계 입력값 | ON |
| 보내는분 | 발송인 프로필에 저장된 번호 | ON |
| 담당자 | **담당자 저장공간에서 '수신함'인 사람 전원 자동 편입** | ON (이 주문에서만 끌 수 있음) |
| 추가 수신자 | 이 주문 한정, 최대 5명 | 직접 입력 |

**예외**
| 상황 | 처리 |
|---|---|
| 마감(18:30) 이후 접수 | 「즉시배송」 버튼이 「익일 빠른배송」으로 바뀌고 익일 12:30 슬롯 적용 |
| 부고장 링크 파싱 실패 | 자동 입력 없이 직접 입력으로 계속. 실패를 조용히 넘기지 않고 안내 (→ 9.3.1) |
| 우편번호 스크립트 로드 실패 | 주소검색 버튼을 감추고 직접 입력 유지. **주문이 막히면 안 된다** |
| 승인대기·반려·정지 거래처 | **로그인 불가**(2026-09-25 결정) — 포털에 들어오지 못하므로 주문도 없다. 로그인 뒤 상태가 바뀌면 세션을 끊는다(→ 6.2 · 8.2) |

## 3.3 주문 처리 (관리자)

```
접수대기 ──[주문접수 처리]──► 주문접수 ──[사진+인수자 저장]──► 배송완료
    │                             │                              └─ 알림톡 자동 발송
    └──[주문취소]──► 취소 ◄───────┘
                      └─ 사유(코드값) + 수수료 필수
```

- **배송완료는 수동 전환이 아니다.** 주문접수 상태에서 현장사진과 인수자를
  저장하면 자동으로 배송완료가 되고 알림톡이 나갑니다. 사진 없이 완료 처리가
  되지 않게 하는 것이 목적입니다.
- **전이는 앞으로만 갑니다.** 상세 모달의 헤더 스테퍼에서 다음 단계만 누를 수
  있고, 되돌리기는 UI 가 막습니다(잘못 눌렀으면 주문취소를 씁니다).
  `배송완료` 단계는 현장사진·인수자가 모두 있을 때만 활성화됩니다.
  **서버도 같은 전이 규칙을 강제해야 합니다** — UI 차단은 편의일 뿐입니다.
- 상태가 바뀔 때마다 **처리 이력(`history`)에 한 줄이 쌓입니다**(→ 5.3).
- B2B·B2C 가 같은 상태 4종을 씁니다. 화면만 다릅니다.

## 3.4 정산 3단계

```
귀속월 다음 달 · 거래처별 invoiceDay(1~28일) 10:00
   │
   ├─► ① 거래명세서 자동 발급 (전월 귀속)
   │       거래처 포털 · 관리자 정산회계 양쪽에 나타남
   │
   ├─► ② 거래처가 명세서 확인 후 [계산서 발급 동의]  ← 마감까지
   │       동의 후에는 내용을 변경할 수 없음
   │       마감 = 발급월 10일 13:00 (invoiceDay 1~10) / 28일 13:00 (invoiceDay 11~28)
   │       └─ 마감까지 무응답 → **마감 시각에 자동 동의** (agreed_mode = auto)
   │
   ├─► ③ 계산서(면세) 자동 발급 (바로빌 API — 9.1) — 동의 즉시
   │       작성일자 = 귀속월 말일 (1~10 그룹) / 동의한 날 (11~28 그룹, 자동이면 28일)
   │
   └─► ④ 입금 확인 → 정산 완료
           └─ 기한 초과 → 미수금. 대쉬보드·정산 표에 경고
```

- **정산 기한** = 발행일이 속한 달의 **말일**.
  예: 귀속 2026-08, invoiceDay=20 → 발행 2026-09-20 10:00, 동의 마감 2026-09-28 13:00, 기한 2026-09-30.
- **동의 마감이 발급일 그룹으로 갈리는 이유** — 세법상 계산서는 공급시기(귀속월)의 **익월 10일**까지
  발급해야 전월분으로 귀속됩니다. 발급일이 1~10일이면 10일까지 동의를 받아 귀속월 말일자로 소급
  발급할 수 있고, 11~28일이면 소급이 불가능해 **동의한 날짜**로 발급됩니다. 그래서 **작성일자 규칙이
  그룹마다 다릅니다.** (2026-09-17 운영 확정. 프런트의 단일 소스는 `js/data/settlement-rules.js`,
  회귀 테스트 `tools/test-settlement-rules.mjs`.)
  - 예 1 — invoiceDay=1, 귀속 2026-08: 발행 9/1 10:00 → 마감 9/10 13:00 → 9/3 동의 → 작성일자 **8/31**.
    미동의면 9/10 13:00 자동 동의, 작성일자 역시 8/31.
  - 예 2 — invoiceDay=15, 귀속 2026-08: 발행 9/15 10:00 → 마감 9/28 13:00 → 9/17 동의 → 작성일자 **9/17**.
    미동의면 9/28 13:00 자동 동의, 작성일자 **9/28**.
- **미수가 쌓여도 주문을 자동으로 막지 않습니다** (2026-09-17 결정). 기한 초과(`OVERDUE`)는 대쉬보드
  미수금 KPI·정산 표 경고와 정산담당 알림톡(→ 9.4)으로 알리고, 반복되면 관리자가 거래처 상태를 `정지` 로
  바꿔 **수동으로** 막습니다. 신용 한도 컬럼·자동 차단 규칙은 두지 않습니다 — 후불 거래에서 차단은 영업 결정입니다.
  정지하면 **로그인 자체가 막혀**(→ 6.2) 명세서·정산 화면도 볼 수 없으니, 미수 안내는 알림톡(→ 9.4)으로 갑니다.
- **발급일(`invoice_day`) 변경은 다음 달 발급분부터 적용합니다** (2026-09-17 운영 확정).
  변경한 달을 귀속월로 하는 명세서(= 다음 달에 발급되는 것)부터 새 발급일을 쓰고, **이미 발급된 달은
  옛 발급일로 계산된 채 그대로 둡니다.** 계약 조건 변경이 미래에 적용되는 것과 같은 취급입니다.
  - 예: 2026-09-17 에 15일 → 1일로 변경 → 귀속 2026-09(발급 2026-10-01)부터 1일. 귀속 2026-08 은
    발행 2026-09-15 · 마감 2026-09-28 13:00 · 작성일자 2026-09-17 그대로.
  - ⚠️ **과거 레코드를 재계산하지 마십시오.** `Settlement` 의 `issue_date`·`agree_deadline_at`·`doc_date` 는
    생성 시점에 확정되는 값입니다. 재계산하면 이미 동의·발급이 끝난 달의 **계산서 작성일자가 소급해
    바뀌어** 국세청 발급분과 대사가 되지 않습니다(프런트에서 실제로 재현된 결함입니다 — 수동 동의한
    달의 작성일자가 09-17 → 08-31 로 밀리고, 자동 동의분이 '동의대기' 로 되돌아가 거래처 포털에 동의
    버튼이 다시 떴습니다).
  - 프런트는 거래처 레코드의 `invoiceDayLog`(적용 시작 귀속월 + 이전 값)로 이 규칙을 구현합니다(→ 4.2).
- **약관 조항(초안 · 법무 검토 전제, 2026-09-17 채택).** 프런트 단일 소스는 `js/data/terms.js`(`TERMS_VERSION`).
  "기한 내 의사표시가 없으면 동의로 본다"는 의제는 **상당한 기한 + 명확한 별도 고지**가 있어야 유효로 봅니다
  (약관규제법 제12조 — 검토 필요). 그래서 마감 전날 알림톡(9.4)은 이 조항의 요건입니다.
  > **제N조 (거래명세서 및 계산서 발급 동의)**
  > ① 회사는 매월 거래처가 지정한 발급일 10:00에 전월 귀속 거래명세서를 거래처 포털에 발급하고 정산·회계 담당자에게 통지한다.
  > ② 거래처는 발급일이 1일~10일인 경우 발급월 10일 13:00까지, 11일~28일인 경우 발급월 28일 13:00까지 명세서 내용을 확인하고 계산서 발급에 동의하거나 이의를 제기하여야 한다.
  > ③ 회사는 제2항 기한 전날 담당자에게 기한과 미응답 시 처리 내용을 별도로 고지한다.
  > ④ 제2항 기한까지 동의 또는 이의의 의사표시가 없는 경우, 거래처는 해당 명세서 금액으로 계산서 발급에 동의한 것으로 본다.
  > ⑤ 계산서 작성일자는 발급일이 1일~10일인 경우 귀속월 말일, 11일~28일인 경우 동의일(제4항의 경우 동의 기한일)로 한다.
  > ⑥ 발급된 계산서는 취소·수정할 수 없으며, 명세서 발급 후 취소된 주문의 수수료는 다음 달 정산에 반영한다.
- **전 품목이 면세**(생화·화환)라 발급 문서는 **계산서**입니다. '세금계산서'·VAT 표기를 쓰지 않습니다.
- **명세서 동의·계산서 발급 상태는 발행일 이후에만 성립합니다.** 발행일이 아직 오지 않은 귀속월은
  `SCHEDULED` 로 내려보내고 화면은 '발급예정' 으로 찍습니다 — 화면은 서버 상태를 그대로 찍습니다
  (데모에서 월 오프셋으로 찍다가 invoiceDay 가 큰 거래처에서 발행 전인 달이 발급완료로 보이던
  결함이 있었습니다).
- **자동 동의는 서버 잡이 만듭니다.** `agree_deadline_at` 이 지난 `AWAITING_AGREEMENT` 레코드를
  `AGREED(agreed_mode=auto, agreed_at=agree_deadline_at)` 로 바꾸고 곧바로 ③을 호출합니다. 프런트
  데모는 기록 없이 매번 파생하지만(과거 달 백필 회피), 서버는 **기록**해야 합니다 — 감사 로그 대상입니다.
- 관리자는 정산 표에서 청구금액을 눌러 **청구 근거**를 그 자리에서 펼쳐 봅니다.
  ⚠️ 근거는 **청구금액과 같은 집합에서** 나와야 합니다 — 화면은 품목별
  (상품 · 건수 · 금액)로 묶고 마지막 줄에 합계를 찍는데, 그 합계가 청구금액과
  다르면 청구서를 신뢰할 수 없습니다.
- 관리자 표의 동의·발급 칸은 **배지 + 날짜·구분**(수동/자동 · 마감 · 작성일자)입니다 — 응답에 그 값이
  있어야 합니다(→ 6.6).

**예외**
| 상황 | 처리 |
|---|---|
| 마감까지 동의 없음 | **마감 시각(13:00)에 자동 동의** 후 계산서 발급. 근거는 약관 조항(아래 초안)과 마감 전날 알림톡(→ 9.4) |
| 정산·회계 담당자가 없는 거래처 | 마감 임박·자동 동의 알림톡을 **보내지 않고**(대체 수신자 없음, 2026-09-17 결정) 관리자 정산 표에 '알림 수신자 없음' 경고를 띄운다. 자동 동의는 그대로 진행한다 — ⚠️ 사전 고지 없는 의제라 법무 검토 필요. 이관 시드 기준 19곳 중 18곳이 해당 |
| 마감 후 동의 요청 | `409 SETTLEMENT_ALREADY_AGREED` — 이미 자동 동의된 레코드. 화면은 마감이 지나면 버튼을 주지 않는다 |
| 관리자 대리 동의 | **이번 범위 밖** — 화면·API 모두 없음 (2026-09-17 결정). 필요해지면 `agreed_mode=admin` 추가 |
| 부분 입금 | **받지 않는다** (2026-09-17 결정). 전액이 들어올 때까지 `미입금` 이고 미수금 KPI 에도 전액이 잡힌다. 잔액 이월·부분 기록 없음 — 사정은 관리자 메모로만 남긴다 |
| 계산서 발급 실패 | 재시도 후 관리자 알림. 수기 발급으로 폴백 (→ 9.1) |
| 명세서 발급 후 주문 취소 | 취소 수수료가 **그 달 정산에 가산**된다. 이미 발급된 명세서는 수정 불가 → 다음 달 반영 |

## 3.5 거래명세서 공개 링크 열람

```
관리자 정산회계 › [링크 복사]
   └─ 토큰 발급: (거래처ID, 사업자번호, 귀속월) 3튜플이 같으면 같은 토큰 재사용
      /invoice/?link=<10자 토큰>
         └─ 로그인 없이 문서가 열린다 (capability URL)
```

⚠ **현재 만료·열람 로그가 없습니다.** 링크를 아는 사람이 곧 열람 권한자이며,
명세서에는 그 달 전체 주문(배송지·발송인·금액)이 들어 있습니다. 서버 전환 시
8.3의 정책을 반드시 함께 구현해야 합니다.

## 3.6 주문서 등록 (관리자 · 2단계 위저드)

주문 **상세** 모달과는 **다른 모달**입니다. 상세는 이미 있는 주문을 고치는
상시 편집 화면이고, 등록은 아직 없는 주문을 만드는 2단계 위저드입니다.

```
B2C  #/admin/b2c › [신규 주문 등록]
  1단계 주문경로 · 결제          채널·결제 상태는 주문서에 적힌 사실일 뿐(집계에 쓰지 않는다)
     └─ 주문 담당자(내부) — 칩 라디오, 선택사항. 고르지 않으면 미지정으로 등록된다
  2단계 주문서 작성              주문자 · 발주정보
     └─ [주문 등록] → 이때 비로소 채번한다

B2B  #/admin/orders › [신규 주문 등록]
  1단계 거래처                   계약단가·거래 조건·월 청구가 여기서 갈린다
     └─ 주문 요청자(거래처 담당자) · 주문 담당자(내부) — 각각 별도 카드, 인라인 선택
  2단계 상품 · 단가 + 발주정보    계약단가 판정 · 배송완료 알림 수신 명단
     └─ [주문 등록] → 채번 + 첫 이력 `created`
```

**헤더 [자동작성] — 두 위저드 공통입니다.** 소스가 **셋**이고 **입력의 종류가
다릅니다**: 부고장 링크 · 청첩장 링크 · **텍스트 인식**. 앞 둘은 URL 을 받아
배송지·받는분·연락처를(청첩장이면 예식 일시까지) 2단계 발주정보에 채우고(→ 9.3.1),
**텍스트 인식은 거래처가 카카오톡·문자로 보낸 평문 주문서 원문**을 받습니다(→ 9.3.2).
링크 모드는 포털 4단계(→ 3.2)와 **같은 파싱 계약**을 쓰므로 서버가 호출 화면을
구분하지 않지만, **텍스트 인식은 관리자 등록 모달 둘 뿐입니다** — 포털 퍼널에는
없습니다(손님이 남의 주문 문자를 붙여 넣는 자리가 아닙니다).

인식에 실패해도 다이얼로그를 닫지 않고 그 자리에서 안내합니다 — 닫고 토스트로 알리면
방금 붙여 넣은 원문을 잃습니다. 링크 모드는 인식된 `kind` 가 고른 세그먼트와 다르면
**어느 세그먼트로 바꾸면 되는지 지목**하고 붙여 넣은 값을 그대로 둡니다.
자동작성은 **스텝을 강제로 넘기지 않습니다**.

**주문번호는 등록을 확정할 때 발급합니다.** 모달을 열 때 채번하면 등록하지 않고
닫아도 번호가 영구히 소모됩니다. 취소는 번호를 소비하지 않습니다.

**첫 이력은 `created`** (`주문 접수 · <채널 또는 거래처명>`) 입니다.

**신규 주문의 담당자는 미지정으로 시작합니다.** 자동 배정하면 '담당자 미지정 주문을
열면 피커가 자동으로 뜬다'는 장치가 신규에서 죽습니다. API 자동 등록 건과 같은 상태로
시작하는 것이 맞습니다.

**등록 후 목록 복귀** — 현재 탭·기간 필터 때문에 방금 등록한 주문이 안 보일 수 있습니다.
보이지 않을 때만 탭·기간을 전체로 되돌리고 **그 사실을 토스트로 알립니다**. 말없이
사라지는 것도, 말없이 필터를 푸는 것도 둘 다 나쁩니다(검색어는 건드리지 않습니다).

**거래처 목록은 `활성`만 노출합니다.** 정지·반려 거래처의 주문이 그 달 청구에 들어가면
안 됩니다. 검색 결과가 비면 그 이유를 화면에서 말해 줍니다.

# 4. 기능 명세

화면별 필드·검증 규칙·상태 전이입니다. 필드명은 프런트 구현과 동일합니다.

## 4.1 공통 규칙

| 항목 | 규칙 |
|---|---|
| 연락처 | 숫자만 입력받아 `010-0000-0000` 으로 자동 하이픈. 저장은 하이픈 포함 |
| 사업자번호 | `000-00-00000`. 비교·중복 판정은 **숫자만 추출**해서 수행 |
| 금액 | 정수(원). 표시만 천단위 구분 |
| 날짜 | 저장 `YYYY-MM-DD`, 주문일시 `YYYY/MM/DD HH:mm` |
| 빈 값 | 표에서 `—`. 서버는 `null` 과 `""` 를 구분하지 않아도 된다 |

## 4.2 거래처 (`#/admin`)

| 필드 | 타입 | 필수 | 비고 |
|---|---|---|---|

전문을 띄웁니다. 담당자가 발주를 확정하기 직전에 한 번 더 보게 하는 자리입니다.
목록에는 표시하지 않습니다 — 모달이 전문을 띄우므로 배지는 중복입니다.

**정산 귀속월** = 주문일시의 년·월. 주문이 어느 달 정산에 들어가는지가
모달에 표시됩니다.

**화면은 B2C 통합주문관리(4.4)와 동일합니다.** 같은 일을 하는 두 화면이
다르게 생기면 담당자가 화면마다 조작을 다시 배웁니다. 필터 카드 3층 ·
11열 표 · 상세 모달 · 담당자 지정 · 현장사진 업로드까지 같은 코드를
씁니다(`js/util/order-screen.js`). **두 화면은 필드 서술자 배열만 다릅니다.**

**목록 행 배경색** — 현황 배지 한 칸만으로는 44행짜리 표에서 '오늘 나갈 건'을
찾기 어렵습니다. 행 전체를 옅게 칠해 덩어리로 읽히게 합니다. 판정은
`js/util/date.js` 의 `orderRowTone()` 한 곳이며 **세 화면이 공유**합니다
(`#/admin/b2c` · `#/admin/orders` · `#/app/orders`).

| 조건 | 행 배경 |
|---|---|
| 접수대기 (배송일 무관) | 연노랑 |
| 주문접수 · 배송일이 **오늘이거나 이미 지남** | 연핑크 |
| 주문접수 · 배송일이 **오늘 이후** | 연파랑 |
| 배송완료 | 흰색(기본) |
| 취소 | 연회색 |

지연(배송일이 지났는데 아직 주문접수)은 **가장 급한 건**이라 당일건과 같은
덩어리로 묶습니다. '오늘'은 달력일 기준이며, 배송일을 읽을 수 없으면 칠하지
않습니다 — 틀린 색보다 무색이 낫습니다.

**행 아무 데나 누르면 상세 모달이 열립니다.** 11열 표에서 오른쪽 끝 연필까지
커서를 옮기지 않아도 되게 한 것이고, 연필(포털은 카메라) 버튼은 같은 일을 하는
명시적 컨트롤로 남습니다 — 키보드 접근은 그 버튼이 담당합니다. 셀 안 텍스트를
드래그해 선택하는 동작은 그대로 살아 있습니다.

**목록 정렬 = 위 색 순서 그대로**입니다(노랑 → 핑크 → 파랑 → 흰색 → 회색).
다른 정렬 기준은 두지 않습니다 — 색이 급한 순서인데 줄 순서가 다르면
"노란 줄이 위"라는 눈의 기대가 깨집니다. 같은 색 안에서는 **원래 순서를
유지**합니다(안정 정렬). 서버가 목록을 내려줄 때도 같은 순서를 권합니다.

**상세 모달 구조** (읽기↔편집 토글은 없습니다 — 모드 없는 상시 편집입니다):

| 영역 | 내용 |
|---|---|
| 헤더 | 주문번호 · 상태 배지 · **3단 스테퍼**(상태 전환) · 담당자 pill(점 색 = 지정 초록 / 미지정 주황) · `···` 메뉴 · 닫기 |
| 좌측 레일(다크) | 배송 현장사진(3:4) · 인수자 성함 · 처리 메모 |
| 본문 카드 | **주문정보**(고객 접수 내용) · **발주정보**(화원 전달 내용) |
| 우측 레일 | 요약(배송일시까지 남은시간 / 지났으면 **경과 시간**) · **처리 이력**(시간순, 최신이 맨 아래) · **거래 조건**(B2B) — 세 장 모두 같은 카드 골격 |
| 푸터 | `수정한 항목 N개` · 닫기 · 변경사항 저장 |

`···` 메뉴에 **주문취소**와 **주문서 삭제**가 들어갑니다. 삭제는 '되돌릴 수
없음'을 확인해야 활성화됩니다. 저장해도 모달은 닫히지 않습니다.

**평소에는 모달 안에서 스크롤하지 않습니다.** 주문 하나를 스크롤 없이 처리한다는
전제라 자리가 모자라면 현장사진이 먼저 줄고, 그다음 거래 조건 카드가 양보합니다.
축소 여력을 다 쓰고도 모자라면 **원장 본문이 스크롤을 받습니다** — 컨테이너는
`overflow: hidden` 을 유지합니다(컨테이너를 스크롤시키면 다크 레일까지 같이 밀려
아래에 흰 띠가 드러납니다). 임계 높이는 레코드마다 다릅니다(1280 폭 실측 ≈700~760px).
처리 이력과 거래 조건 카드는 길이가 데이터에 따라 달라져 별도로 자체 스크롤을 가집니다.

| `manager` | 공통 | 배정 담당자. API 자동 등록 건과 신규 등록 건은 공란입니다 |
| `ribbonPhrase` / `ribbonSender` | 공통 | 리본 문구·보내는분 |
| `deliverAt` | 공통 | 배송 희망일시. **배송모드(즉시/지정)는 저장하지 않습니다**(2026-09-17 결정) — 포털의 즉시배송 세그먼트는 이 값을 채우는 자동입력일 뿐이고, 목록의 당일/예약 색은 이 값과 오늘의 비교로 파생합니다 |
| `image` | 공통 | 현장사진 (dataURL) |
| `notified` | 공통 | 알림톡 발송 여부 — 배송완료 시 자동 `true` |
| `history` | 공통 | 처리 이력 (→ 5.3) |

**채널 수수료·정산 주기라는 개념은 없습니다** (2026-09-17 결정 — 디자인 단계에서 잘못 들어간 것이라
화면·데이터에서 걷어냈습니다). `B2C_CHANNEL_META` 는 채널 설명 한 줄만 갖고, `pay_status` 는 주문서에
적힌 사실로만 남습니다(집계에 쓰지 않음). B2C 정산은 외부 채널 정산서가 원본입니다(→ 10.3).

## 4.5a 거래처 담당자 관리 (관리자 · 다이얼로그)

거래처별 담당자를 **관리자가** 보고 고치는 다이얼로그입니다. 4.6 의 거래처 포털 화면과
**같은 레코드**(→ 5.8)를 다루며, 불변식도 같습니다.

| 항목 | 규칙 |
|---|---|
| 진입점 | 거래처 목록(`#/admin`) '관리' 열의 사람 아이콘 · 거래처 수정 모달 레일의 '정산·회계 담당자' 카드 |
| 목록 배지 | 사람 아이콘에 등록 인원수를 함께 찍습니다 — 0명인 거래처가 목록에서 바로 보여야 합니다 |
| 본문 | 그 거래처의 담당자 표(이름 · 부서·직위 · 연락처 · 알림톡 수신 · 정산담당 · 삭제) |
| 불변식 | 담당자가 1명 이상이면 정산·회계 담당은 **정확히 1명**. **정산담당은 직접 삭제할 수 없습니다** — 삭제 자리에 잠긴 표시를 남겨 이유를 말합니다 |
| 첫 담당자 | 비어 있던 거래처에 처음 추가되는 담당자가 자동으로 정산담당이 됩니다 |

**왜 거래처 수정 모달 본문이 아니라 별도 다이얼로그인가** — 모달의 본업은 거래처 원장이고,
담당자는 편집 규칙이 따로 삽니다. 다만 관리자가 담당자를 고칠 경로 자체를 없애면
안 됩니다: 이관 거래처 19곳 중 **18곳이 담당자 0명**이고(구 시스템에 대응 필드가
없었습니다 → 10.2), 담당자는 주문 요청자·배송완료 알림 수신자·정산 명세서 수신자의
출처입니다. 거래처 수정 모달은 좌측 레일에 **읽기 전용** '정산·회계 담당자' 카드만
두고 이 다이얼로그를 엽니다(원장 위에 스택되므로 작성 중인 편집이 유지됩니다).

## 4.6 프로필 · 담당자 저장공간 (`#/app/profile`)

- **발송인 프로필** — 성함·직위·고정문구·배송완료 수신번호. **거래처별**(→ 5.9). 주문 3단계에서
  꺼내 쓰는 값이며, 주문 시 보내는분 알림 번호로 자동 연결됩니다.
- **담당자** — 이름·부서·연락처·메세지 수신여부·정산담당 여부.
  - **메세지 수신여부가 ON 인 담당자는 모든 주문의 알림 수신자로 자동 편입**
    됩니다. 주문서에서 건별로 끌 수 있으나 저장공간 설정은 바뀌지 않습니다.
  - **정산·회계 담당자는 항상 1명 존재**해야 합니다. 마지막 1명을 해제하면
    첫 담당자가 자동 지정되고, **정산담당은 직접 삭제할 수 없습니다**(다른 담당자를
    먼저 지정해야 합니다).
  - 담당자는 **거래처별**입니다(→ 5.8). 이 화면과 관리자의 거래처 담당자 관리 다이얼로그(→ 4.5a)가
    **같은 레코드**를 고칩니다 — 한쪽에서 바꾸면 다른 쪽에도 그대로 보입니다.

## 4.7 상품 단가 (`#/admin/pricing`)

- 카탈로그 21종(4개 카테고리)이 기준 단가를 갖습니다. **수는 `store.ALL_PRODUCTS` 가 정본**입니다 — 상품이 늘면 이 문장도 같이 고치세요(2026-09-17 에 생화 '특대 꽃바구니' 가 추가돼 20 → 21 이 됐습니다).
- 거래처별 단가를 덮어쓸 수 있으며, 저장하면 포털 「상품 규격 안내」와
  주문서 적용 단가에 즉시 반영됩니다(읽는 곳 2군데 — 4.2·5.x 참조).
- 화면은 **좌측 거래처 목록(검색) + 분류 아코디언 + 저장 전 변경 패널** 구조입니다.
  거래처를 옮겨도 미저장 편집은 메모리에 남고, 목록에 미저장 표시가 붙습니다.
  저장은 **보고 있는 거래처 1곳**에만 적용됩니다 — 일괄 저장 API 는 없습니다.
- 세는 값이 둘이고 의미가 다릅니다. 응답·로그에서 섞이지 않게 할 것:

  | 지표 | 정의 |
  |---|---|
  | **맞춤** | 카탈로그 정가와 **다른** 단가가 걸린 상품 수. 정가와 같은 값을 명시 저장한 건 포함하지 않습니다 |
  | **가격변동** | 저장된 값과 달라진 상품 수(= 아직 저장되지 않은 편집). 클라이언트 전용 개념 |

- 오버라이드 값은 **양수 정수만** 유효합니다. `0`·빈 값·누락은 전부 "정가"라는 한 상태로
  정규화합니다 — 세 값을 구분하면 "변경 없음"이 변경으로 잡힙니다.
- **정가와 같은 값은 오버라이드로 저장하지 않습니다.** 청구액은 같지만, 나중에 카탈로그
  정가가 오르면 그 잔재가 조용히 할인으로 되살아납니다. 서버도 같은 규칙으로 거를 것.
- 입력 검증(클라이언트 기준, 서버도 같게 할 것): 숫자·쉼표·공백만 허용하고 **그 외는 거부**합니다.
  숫자 이외를 제거하는 방식은 금지 — 구분자가 사라지며 자릿수가 이동합니다
  (`12345.67` → 1,234,567 = 100배). 앞자리 `0`, 상한(**1,000만원**) 초과도 거부합니다.
- **적용 단가 규칙은 한 곳에만 둡니다** — `store.appliedPrice(clientId, product)`.
  포털 상품안내·포털 주문 퍼널·관리자 주문서가 각자 복제하다 주문 퍼널만 빠져,
  같은 거래처가 화면마다 다른 금액을 보던 결함이 있었습니다. API 도 단가 파생을
  한 엔드포인트/한 함수로 묶을 것.
- **단가 변경 이력은 두지 않고, 기존 주문에 소급하지 않습니다** (2026-09-17 결정). `ClientPrice` 는
  현재값만 갖고, 주문의 `amount` 는 접수 시점 값이 그대로 남습니다(프런트도 이미 스냅샷이라 코드 변경 없음).
  화면의 '저장 전 변경 패널'은 저장 직전까지만 보여 주고 영속화하지 않습니다.

## 4.8 대쉬보드 (`#/admin/dashboard`)

**모든 수치는 목록 화면과 같은 소스에서 파생**합니다. 대쉬보드 전용 집계
테이블을 두면 화면 간 숫자가 어긋나 신뢰를 잃습니다.

| 블록 | 내용 |
|---|---|
| KPI 5장 | 통합매출 / B2C / B2B / 채널별 / 미수금. 각 카드에 건수와 전월 대비 증감 |
| 액션 큐 | 접수대기 · 미완료처리 탭. **남은시간 오름차순** — 급한 건이 항상 위 |
| 통합매출 추이 | 최근 6개월 정산 매출 + 연속 증가 개월 수 |
| 가입 승인 대기 | 대기 건이 있을 때만 표시 |
| 상품별 이용 비중 | 9종 도넛 + 순위 막대. 전체/채널 전환 |
| 거래처 계약 통계 | `joinDate` 누적. 월별(12) / 년별(3) 전환 |
| 정산 진행 | 지난 달 귀속 4단계(명세서·동의·계산서·입금) |

**매출 채널** — 거래처의 `channel` 이 `일반` 이 아니면 B2B 합계에서 빠져 자기
KPI 카드를 갖습니다. 사업 성격이 다른 거래처의 매출을 따로 보기 위한 장치이며,
현재 `고이` 하나가 지정돼 있습니다.

**남은시간** — 도착희망 시각까지의 잔여. B2C 는 `deliverAt` 실값, B2B 는 **주문일의
당일배송 마감(18:30)** 을 도착 기준으로 삼습니다. B2B 레코드에도 `deliverAt` 은
있지만(→ 4.3 · 5.3) **대쉬보드 큐만 그것을 보지 않습니다** — `etaOf()` 의 B2B 분기가
`deliverAt` 대신 `o.date` 에 당일배송 마감을 얹습니다. 서버 전환 시 이 분기를
`desired_arrival_at` 실값으로 맞출 것.

시각이 **이미 지난 건은 얼마나 지났는지까지 적습니다**(`1시간 경과` ·
`3일 2시간 경과`). '경과' 한 마디만 있으면 15분 늦은 건과 사흘 묵은 건이 같아
보여 어느 쪽을 먼저 잡을지 판단할 수 없습니다. 표기는 큰 단위 둘까지만 쓰고
0 인 작은 단위는 뺍니다(`1일`, `2시간 40분`, `15분`).

## 5.3 Order

B2B·B2C 를 **한 테이블 + `kind` 컬럼**으로 둘지, 두 테이블로 나눌지는
구현 판단입니다. 화면은 분리돼 있고 공통 컬럼은 아래 정도입니다.

| 구분 | 컬럼 |
|---|---|
| 공통 | `id`·`order_no`·`status`·`address`·`product_name`·`amount`·`ordered_at`·`delivered_at`·`photo_url`·`receiver`·`memo`·`cancel_reason`·`cancel_fee`·`staff_id` |
| 공통(추가) | `desired_arrival_at`·`recipient_name`·`recipient_phone`·`ribbon_phrase`·`ribbon_sender`·`notified`·`orderer_name`·`request` |
| B2B 전용 | `client_id`·`settle_period`(YYYY-MM)·`requester_contact_id`·`requester_name`·`requester_phone` |
| B2C 전용 | `channel`·`orderer_phone`·`pay_status` |
| B2B 전용(등록) | `profile_id` — 리본 보내는분 명의의 출처. `ribbon_sender` 문자열은 **저장 시점 스냅샷**이라 프로필이 나중에 바뀌어도 인쇄된 리본과 어긋나지 않습니다. **B2C 에는 없습니다** — 관리자 B2C 등록의 '보내는분'은 자유 입력이고, 프로필 피커는 B2B 등록 모달에만 있습니다(→ 10.4 Q14) |

**`orderer_name`·`request` 는 공통입니다 — 라벨만 다릅니다.** B2C 는 '주문자'(익명 개인),
B2B 는 '발송인'(거래처 담당자)으로 표기할 뿐 같은 컬럼입니다(→ 4.4). `request`(요청사항)도
양쪽 모두 씁니다. B2C 에서 `orderer_name` 은 등록 필수값이라 B2B 전용으로 두면 등록이 막힙니다.
연락처는 다릅니다 — `orderer_phone` 은 B2C 전용이고, B2B 는 거래처 대표 연락처를 읽습니다.

**주문번호는 등록 확정 시 발급합니다 — 취소는 번호를 소비하지 않습니다**(→ 3.6).

**요청자는 id + 스냅샷을 함께 남깁니다.** `requester_contact_id` 만 두면 담당자가
삭제됐을 때 과거 주문이 "누가 요청했는지"를 잃고(주문은 감사 근거입니다), 이름만 두면
동명이인에서 갈립니다. **`requester_contact_id` 가 `NULL` 인 경우가 정상입니다** —
담당자 목록에 없는 사람을 직접 입력한 건으로, 이름·연락처만 주문에 남습니다.
(이관 거래처 19곳 중 18곳이 담당자 0명이라, 이 경로가 없으면 등록 자체가 막힙니다.
등록 화면도 그 비율에 맞춥니다 — 담당자가 **0명이면 이름·연락처 칸이 처음부터 열려**
있고, 담당자가 있는 거래처에서만 프로필 목록이 펼쳐지며 그 아래 '직접 입력' 행을 고르면
같은 칸이 열립니다. 따라서 `NULL` 이 다수가 됩니다.)

**처리 이력** — 주문마다 `OrderHistory` 를 별도 테이블로 둡니다(주문 1 : 이력 N).
**`at` 오름차순(오래된 것이 먼저)** 으로 내려주세요 — 화면이 위에서 아래로
시간순으로 읽히고, 새 이력은 카드 아래쪽에 붙습니다. 프런트는 `order.history`
배열을 **정렬 없이 그대로** 그립니다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `order_id` | FK | |
| `type` | enum | `created`·`manager`·`status`·`edit`·`delivered`·`cancel`·`photo` — 점 색을 결정 |
| `label` | text | 담당자가 읽을 한 줄(예: `상태 변경 · 주문접수`) |
| `at` | datetime | 분 단위(`YYYY-MM-DD HH:mm`)로 표기합니다 |
| `actor_id` | FK, nullable | 누가 한 일인지. API 자동 등록 건은 `NULL` |

이름은 프런트의 `HIST_DOT`(`js/data/order-history.js`) 키와 **글자 그대로 같아야**
합니다 — 모르는 값이 오면 점이 조용히 기본 회색으로 떨어집니다. `created` 는 주문의
**첫 줄**이고(예전에는 `edit` 이 첫 줄이라 "언제 생긴 주문인지"를 이력만 보고는 알 수
없었습니다), `delivered`(`배송완료 · 알림톡 발송`)는 **성공색 점을 갖는 유일한 항목**
이므로 상태 변경 일반(`status`)과 반드시 구분해서 써 주세요. `edit` 의 라벨은
`주문 정보 수정 N건` 입니다. `received`·`save` 라는 이름은 쓰지 않습니다.

**배송완료 알림 수신자** — 주문마다 `OrderNotifyRecipient` 를 별도 테이블로 둡니다
(주문 1 : 수신자 N).
**명단을 만드는 화면은 지금 B2B 뿐입니다** — 거래처 포털 주문과 관리자 B2B 등록 모달만
수신자 토글을 갖습니다. 관리자 B2C 등록은 명단 없이 `notified` 플래그만 씁니다(→ 10.4 Q14).
테이블 자체는 주문 공통으로 두고, B2C 건은 행이 0개인 상태로 시작하면 됩니다. 건별 ON/OFF 는 **이 테이블에만** 기록하고 담당자 저장공간의
`receive_alimtalk` 은 건드리지 않습니다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `order_id` | FK | |
| `kind` | enum | `recipient`(받는분)·`sender`(보내는분)·`contact`(담당자·요청자)·`extra`(추가 수신자) |
| `contact_id` | FK, nullable | `kind=contact` 이고 담당자 저장공간에서 온 경우에만 |
| `profile_id` | FK, nullable | `kind=sender` 인 경우 |
| `name` / `phone` | string | **저장 시점 스냅샷.** 원본이 지워져도 누구에게 보냈는지 남습니다 |
| `on` | bool | 이 주문에서의 수신 여부 |

⚠️ **건별 OFF 의 키는 담당자 `id` 입니다.** 표시 순번(`no`)은 쓰기마다 다시 매겨지므로
키로 쓰면 담당자 1명을 지웠을 때 **엉뚱한 사람의 알림이 꺼집니다**. 추가 수신자는
최대 5명입니다.

> 이력은 **서버가 씁니다.** 프런트가 보내는 배열을 그대로 믿으면 안 됩니다.
> 상태 변경·담당자 지정·저장·취소·사진 업로드 시점에 서버가 append 하고,
> 감사 로그(8.4)와 달리 **담당자에게 보여주는 것이 목적**이라 내용이 짧습니다.
> 같은 값으로 다시 저장하는 요청은 이력을 남기지 않습니다(중복 방지).

**상태**: `PENDING`(접수대기) → `ACCEPTED`(주문접수) → `DELIVERED`(배송완료),
그리고 `CANCELED`(취소). 전이는 4.3·3.3 참조.

**불변식**
- `DELIVERED` 는 `photo_url` 과 `receiver` 가 모두 있어야 한다.
- `CANCELED` 는 `cancel_reason` 이 있어야 한다.
- `settle_period` 는 `ordered_at` 의 년·월. **명세서 발급 후에는 변경 불가.**

> **`desired_arrival_at` 은 B2B·B2C 공통입니다(결정됨).** 포털 주문 2단계에서
> 받는 값이고, 프런트 목데이터에도 양쪽 다 실려 있습니다. 두 주문 화면이
> 같은 '주문 / 배송일시' 2행 셀을 쓰므로 한쪽에만 두면 열이 비어 버립니다.
>
> ⚠ **`photo_url` 과 `notified` 도 공통입니다.** B2B 에 있던 `hasPhoto`(bool)는
> 없앴습니다 — 사진의 존재 여부와 사진 자체를 따로 들고 있으면 반드시
> 어긋납니다. 대쉬보드의 '사진 미등록' 큐도 `photo_url` 로 판정합니다.

## 5.6 RegionRule (지역 규칙)

구 반입 규칙 25건과 기존 배송비 규칙 13건을 한 테이블에 합쳤습니다.

| 컬럼 | 설명 |
|---|---|
| `type` | `BLOCKED`(배송불가) · `ALLOWLIST`(이 상품만 반입) · `SURCHARGE`(추가 배송비) |
| `sido_kw[]` | 시·도 키워드 (전남, 전라남도) |
| `region_kw[]` | 지역 키워드 (밀양) |
| `place_kw[]` | 장소 키워드 (밀양농협). 있으면 장소 한정 규칙 |
| `allow[]` | 허용 상품 **접두사** (3단화환, 쌀화환) |
| `fee` | 추가 배송비(원) |
| `notice` | 사용자에게 보여줄 문구 |

**평가 순서가 곧 정책입니다.**

```
1) BLOCKED            → 즉시 차단, 이하 평가 안 함
2) ALLOWLIST (place)  → 장소 지정 규칙
3) ALLOWLIST (region) → 지역 전역 규칙
4) SURCHARGE          → 금액 가산 (2·3과 동시에 성립 가능)
```

> 밀양은 두 행이 경쟁합니다. 전역은 "쌀화환만", 밀양농협은 "3단화환·
> 근조바구니·쌀화환". 장소 규칙을 먼저 보지 않으면 **밀양농협 주문이 전부
> 반려**됩니다. 회귀 테스트에 상시 포함해야 합니다.

**상품 조건은 접두사 비교입니다.** 구 시스템은 "근조 오브제"처럼 묶어서
적었고 신규 카탈로그는 "근조오브제(1단형)"처럼 규격이 나뉘어 있습니다.
공백을 제거하고 포함 관계로 판정합니다.

> `order.js`·`admin-orders.js` 가 화면에서만 `role name` 으로 대신 보여 줍니다. 서버는 저장을 막는 쪽이고,
> 이미 빈 값인 레코드는 마이그레이션에서 채우거나 사용자에게 채우게 해야 합니다.

주문은 `profile_id` 로 지목하되 `ribbon_sender` 문자열을 함께 남깁니다(→ 5.3).

**거래처별입니다** (2026-09-17 결정). 전역 목록이던 시절 관리자가 태원과학 주문에 다른 회사 명의를
고를 수 있었고, 포털에서 다른 거래처의 프로필이 보였습니다. 프런트는 담당자와 같은 모양의
`profilesByClient` 맵으로 들고 있고, 구 저장본(전역 배열)은 첫 거래처로 이관합니다.

# 6. API 명세

REST + JSON. 모든 응답은 `Content-Type: application/json; charset=utf-8`.
인증은 세션 쿠키(HttpOnly, SameSite=Lax) 또는 Bearer JWT — 8.2 참조.

## 6.1 공통 규약

성공 응답:

```json
{ "data": { } }
```

목록 응답:

```json
{ "data": [], "page": { "cursor": "eyJ...", "hasNext": true, "total": 44 } }
```

에러 응답:

```json
{ "error": { "code": "CLIENT_DEPARTMENT_REQUIRED", "message": "같은 사업자번호가 있어 부서 입력이 필요합니다.", "field": "department" } }
```

| HTTP | 사용 |
|---|---|
| 400 | 입력 검증 실패 (`field` 포함) |
| 401 | 미인증 |
| 403 | 권한 없음 |
| 404 | 없음 (또는 권한 없는 리소스를 감출 때) |
| 409 | 상태 충돌 (이미 취소된 주문, 이미 동의한 정산) |
| 422 | 비즈니스 규칙 위반 (배송불가 지역, 반입 제한) |
| 429 | 레이트 리밋 |

**페이지네이션**은 커서 방식을 권장합니다. 목록 화면이 기간·상태 필터를
자주 바꾸므로 offset 은 중복·누락이 생깁니다.

## 6.2 인증

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/api/auth/login` | `{ accountId, password }` → 세션. 역할과 clientId 반환 |
| POST | `/api/auth/logout` | |
| GET | `/api/auth/me` | 현재 사용자·역할·거래처 |
| POST | `/api/auth/password/reset-request` | 아이디·이메일 → 재설정 메일 |
| POST | `/api/auth/password/reset` | `{ token, newPassword }` |

```json
{ "data": {
  "role": "client",
  "user": { "id": "C003", "name": "(주)진양코퍼레이션", "department": null },
  "permissions": ["order:create", "invoice:read", "settlement:read"]
} }
```

**로그인 실패는 아이디 존재 여부를 노출하지 않습니다.**

```json
{ "error": { "code": "AUTH_FAILED", "message": "아이디 또는 비밀번호가 올바르지 않습니다." } }
```

**식별자는 `accountId` 하나입니다**(2026-09-25 결정). 사업자번호로는 로그인하지 않습니다 — 같은 사업자번호를
여러 계정이 쓰는 것이 정상 시나리오라(부서 분리 → 3.1) 사업자번호로는 계정을 가릴 수 없습니다. 로그인 엔드포인트가
하나이므로 `accountId` 는 거래처·담당자(Staff) 계정을 **통틀어** 유일해야 합니다(프런트는 관리자 아이디를 예약어로 막는다).

**`활성`이 아닌 거래처는 로그인할 수 없습니다**(2026-09-25 결정). 상태는 자격 증명이 맞은 **뒤에만** 봅니다 —
그래야 상태를 알려 줘도 계정 존재가 새지 않습니다. 응답은 `403` + 상태별 코드이고, 화면은 `message` 를 그대로 띄웁니다.

| 상태 | `code` | `message` |
|---|---|---|
| `승인대기` | `ACCOUNT_PENDING` | 가입 승인 심사 중입니다. 승인 안내를 받은 뒤 로그인할 수 있습니다. |
| `반려` | `ACCOUNT_REJECTED` | 가입이 반려되었습니다 (사유: `rejectReason`). 고객센터로 문의해 주세요. |
| `정지` | `ACCOUNT_SUSPENDED` | 이용이 정지된 계정입니다. 고객센터로 문의해 주세요. |

이미 발급된 세션도 같은 규칙을 따릅니다 — 관리자가 정지·반려하거나 거래처를 지우면 그 거래처의 세션을
무효화합니다(→ 8.2). 프런트 데모는 화면을 옮길 때마다 상태를 다시 보고, 끊은 이유를 로그인 화면에 한 번 띄웁니다
(판정·문구의 단일 소스 `js/util/client.js::portalBlock` — 로그인과 라우터가 같이 쓴다).

> `/api/me/contacts` 와 `/api/clients/{id}/contacts` 는 **같은 레코드**를 다룹니다(→ 5.8).
> **최소 1명이 정산담당**이어야 하는 불변식은 두 경로에 똑같이 적용됩니다 — 마지막 정산담당을
> 해제하려 하면 서버가 첫 담당자로 자동 이관하거나 `409` 를 돌려주고, 정산담당 본인은
> `DELETE` 로 지울 수 없습니다(다른 담당자를 먼저 지정해야 합니다).

## 6.8 대쉬보드

화면 블록과 1:1로 대응합니다(→ 4.8). 모두 staff 권한.

| 메서드 | 경로 | 대응 블록 |
|---|---|---|
| GET | `/api/dashboard/kpi?period=YYYY-MM` | KPI 5장 |
| GET | `/api/dashboard/queue?type=pending\|photo` | 액션 큐 |
| GET | `/api/dashboard/revenue-trend?months=6` | 통합매출 추이 |
| GET | `/api/dashboard/product-mix?period=YYYY-MM&channel=` | 상품별 이용 비중 |
| GET | `/api/dashboard/contracts?unit=month\|year` | 거래처 계약 통계 |
| GET | `/api/dashboard/settlement-progress?period=YYYY-MM` | 정산 진행 |

가입 승인 대기 카드는 전용 엔드포인트 없이 `/api/clients?status=PENDING` 을 씁니다.

`GET /api/dashboard/kpi?period=2026-09`:

```json
{ "data": {
  "period": "2026-09",
  "cards": [
    { "key": "total",   "label": "통합매출", "amount": 1795000, "count": 28, "prevAmount": 1230000 },
    { "key": "b2c",     "label": "B2C",     "amount": 335000,  "count": 5,  "prevAmount": 0 },
    { "key": "b2b",     "label": "B2B",     "amount": 1360000, "count": 21, "prevAmount": 1180000 },
    { "key": "고이",     "label": "고이",     "amount": 100000,  "count": 2,  "prevAmount": 50000, "channel": true },
    { "key": "unpaid",  "label": "미수금",   "amount": 36380000, "prevAmount": 34855000, "danger": true }
  ]
} }
```

> **증감률은 클라이언트가 계산합니다.** 서버는 `amount` 와 `prevAmount` 만
> 내려주십시오 — 기준이 0일 때 '전월 기록 없음'으로 표시할지, 무한대로 볼지는
> 표시 규칙이고 서버가 정할 일이 아닙니다.
>
> `b2b` 는 **채널이 `일반` 인 거래처만** 집계한 값입니다. `channel: true` 카드가
> 나머지 채널이며, `total` 은 둘을 모두 포함합니다.

`GET /api/dashboard/queue?type=pending`:

```json
{ "data": [
  { "id": "t1", "kind": "b2b", "orderNo": "B2B-0001",
    "who": "태원과학(주)", "address": "서울 종로구 대학로 101 서울대학교병원 장례식장 3호실",

    "arrivalAt": "2026-09-15T18:30:00+09:00", "arrivalEstimated": true }

```

> `arrivalEstimated: true` 는 **희망 도착시각이 없어 마감시각으로 추정**했다는
> 뜻입니다(B2B). 화면이 추정값임을 표시할 수 있어야 합니다.
>
> 정렬은 `arrivalAt` 오름차순 — 급한 건이 항상 위에 옵니다.

집계 전용 테이블을 만들지 말고 주문·정산 테이블에서 파생하십시오. 화면 간
숫자가 어긋나면 대쉬보드는 쓰이지 않습니다.

## 7.3 강제 지점

1. **모든 `client` 요청은 세션의 `clientId` 로 강제 스코프**합니다. 요청
   본문·쿼리의 `clientId` 를 신뢰하지 마십시오.
2. **`/api/me/*` 와 `/api/clients/{id}` 를 분리**해 두면 실수로 남의 데이터를

   정보입니다(예: 경쟁사의 거래처 ID 추측).
4. 프런트의 화면 분기(`requiresRole`)는 **UX 편의**입니다. 해시만 바꾸면
   우회되므로 권한 경계로 쓰면 안 됩니다.

# 8. 보안

## 8.1 비밀번호

현재 프런트는 비밀번호를 **평문으로 localStorage** 에 둡니다. 데모 전용이며
실서비스에서는 전부 교체해야 합니다.

| 항목 | 요구 |
|---|---|
| 저장 | argon2id 또는 bcrypt(cost ≥ 12). 평문·단방향 해시(SHA) 금지 |
| 관리자 조회 | **불가.** 관리자 화면에는 비밀번호 입력란이 없어야 한다 |
| 재설정 | 임시비밀번호 1회 발급(현재 구현) 또는 재설정 링크 메일 발송(권장) |
| 임시비밀번호 | 최초 로그인 시 **강제 변경**. 유효기간 24시간 |
| 정책 | 8자 이상, 영문+숫자+특수 중 2종 이상. 최근 3개 재사용 금지 |
| 실패 제한 | 5회 실패 시 10분 잠금. 아이디 존재 여부 비노출 |

현재 프런트는 이관 시드 계정에 비밀번호가 없어 **아이디만으로 로그인**합니다
(`login.js` 주석에 명시). 서버 연동 시 가장 먼저 닫아야 할 지점입니다.

## 8.2 세션

| 항목 | 요구 |
|---|---|
| 방식 | HttpOnly · Secure · SameSite=Lax 쿠키 권장 |
| 수명 | 관리자 8시간, 거래처 14일(기억하기 시 30일) |
| 갱신 | 슬라이딩 만료. 관리자는 재인증 없이 24시간 초과 금지 |
| 로그아웃 | 서버 측 세션 무효화 |
| 상태 변경 | 거래처가 `활성`이 아니게 되거나(정지·반려) 삭제되면 **그 거래처의 세션을 즉시 무효화**한다 (→ 6.2) |
| CSRF | 쿠키 세션이면 CSRF 토큰 또는 SameSite=Strict + Origin 검증 |

## 8.3 공개 명세서 링크 (capability URL)

현재 상태: **토큰만 알면 열립니다.** 사업자번호 확인 게이트가 있었으나
사업자번호는 비밀이 아니고 같은 법인의 부서 간 격리도 못 해 제거했습니다.
토큰 자체를 비밀값으로 다룹니다.

| 항목 | 현재 | 서버 전환 시 |
|---|---|---|
| 토큰 | 클라이언트 생성 10자, localStorage | **서버 생성**, 최소 128bit 엔트로피 |
| 논리 키 | (clientId, 사업자번호, 귀속월) | 동일 유지 |
| 만료 | 없음 | **발급 후 60일** (정산 기한 + 여유) |
| 재발급 | 없음 | 관리자가 재발급하면 구 토큰 즉시 무효 |
| 열람 로그 | 없음 | 시각·IP·User-Agent 기록. 거래처 문의 대응 근거 |
| 크롤링 | — | `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer` |
| 레이트 리밋 | — | 토큰당·IP당 분당 20회 |

> 명세서에는 그 달 전체 주문(배송지·발송인·금액)이 들어 있습니다. 유출 시
> 노출 범위가 한 달치 거래 전부이므로 만료와 로그는 선택이 아닙니다.

위 표는 **서버 구현 항목으로 확정**됐습니다(2026-09-17). 프런트 데모는 만료·로그를 흉내 내지 않고,
열람 로그는 감사 로그(8.4)와 같이 **조회 화면 없이 DB 에만** 둡니다 — 거래처 문의가 오면 운영이 조회합니다.

## 8.4 감사 로그

금액·권한이 걸린 동작은 누가 언제 무엇을 바꿨는지 남겨야 합니다. 현재는
기록이 없습니다.

**기록 대상**

| 영역 | 동작 |
|---|---|
| 정산 | 명세서 발급·동의(수동/자동)·계산서 발급·입금 확인·금액 수정 |
| 주문 | 상태 변경·취소(사유·수수료)·금액 수정 |
| 거래처 | 승인·거부(사유)·정지·삭제·**발급일 변경**(적용 시작 귀속월 포함) |

> 단가 변경은 기록하지 않습니다 — 단가 이력을 두지 않기로 한 결정(2026-09-17, → 4.7)과 맞춥니다.
| 계정 | 임시비밀번호 발급·권한 변경·로그인 성공/실패 |

**레코드**

```json
{
  "at": "2026-09-15T10:22:31+09:00",
  "actor": { "type": "staff", "id": "s1", "name": "최고관리자" },
  "action": "SETTLEMENT_PAYMENT_CONFIRMED",
  "target": { "type": "settlement", "id": "C003-202608" },
  "before": { "paidAt": null },
  "after": { "paidAt": "2026-09-15T10:22:31+09:00" },
  "ip": "203.0.113.10"
}
```

**보존 기간** — 금액 관련 5년(세법상 증빙 보존 기간에 맞춤), 그 외 1년.

**조회 화면은 두지 않습니다** (2026-09-17 결정). 조회는 DB·내보내기로 하고, 실제 조사 수요가 생기면
그때 관리자 탭을 붙입니다. 단 **거래처 수정 모달의 '변경 이력' 카드는 이 로그의 거래처 영역을 읽어
채웁니다** — 프런트 데모는 세션 한정 배열이라 모달을 닫으면 사라지는데, 서버에서는 그 자리에 감사
로그(승인·거부·정지·발급일 변경)가 들어가야 합니다.

> **주문 처리 이력(5.3)과 감사 로그는 다른 것입니다.** 이력은 담당자에게
> 주문 상세 모달에서 보여 주는 짧은 진행 기록이고, 감사 로그는 책임 추적용
> 전수 기록(before/after·IP 포함)입니다. 주문 상태 변경처럼 **둘 다 남는
> 동작**이 있지만, 이력을 지운다고 감사 로그가 지워져서는 안 됩니다.

# 9. 외부 연동

## 9.1 바로빌 — 계산서(면세)

구 시스템에서 쓰던 채널을 유지하되 수동 발급을 API 호출로 바꿉니다. **전 품목이 면세**(생화·화환)라
발급하는 문서는 세금계산서가 아니라 **계산서**입니다 — 요청의 과세 유형을 면세로 보내야 합니다.

| 항목 | 내용 |
|---|---|
| 시점 | 정산 동의 완료(수동 또는 마감 시각 자동 동의) **직후** 서버가 호출. 화면은 결과만 본다 |
| 요청 | **전자세금계산서 API(세금계산서 발급 메서드)에 과세유형 `TaxType=면세`** 로 보낸다(2026-09-17 결정 — 바로빌은 전자계산서(면세)를 같은 API 서비스에서 다루고 발급 전 과세유형을 검증한다). 세액 0 · 공급자(도랑플라워) · 공급받는자(거래처 사업자정보) · 품목(월 이용료 합계) · **작성일자 = `Settlement.doc_date`** (1~10 그룹 귀속월 말일 / 11~28 그룹 동의일). 메서드명·필수 필드는 착수 시 개발자센터 레퍼런스에서 확정 |
| 인증서 | **운영이 바로빌 웹에서 공동인증서를 직접 등록**한다(2026-09-17 결정 — 대행사 보관). 전자세금계산서용·전자거래 범용 인증서만 가능(금융거래용 불가). 우리 서버는 API 인증키·회원사 정보만 갖고 **인증서 파일·비밀번호는 시스템을 지나지 않는다** — 등록 API 를 우리 화면에서 부르는 방식은 채택하지 않았다 |
| 응답 | 국세청 승인번호 → `Settlement.einvoice_no`, 발급 시각 → `einvoice_at`, `status=ISSUED` |
| 실패 | 3회 재시도(지수 백오프). 최종 실패 시 관리자 알림 + 대쉬보드 경고. `status` 는 `AGREED` 에 머문다 |

## 9.3 자동작성 파싱 (AI)

자동작성(→ 3.3)의 소스는 셋이지만 **입력의 종류가 둘**이라 계약도 둘입니다 —
**URL 을 받는 링크 파서**(9.3.1)와 **평문 원문을 받는 텍스트 파서**(9.3.2).
둘을 한 엔드포인트로 합치지 마십시오. 가져올 URL 이 있느냐 없느냐로 보안 면(SSRF)과
실패 모드가 갈리고, 프런트도 서로 다른 모듈을 단일 계약으로 두고 있습니다.

### 9.3.1 부고장·청첩장 링크

| 항목 | 내용 |
|---|---|
| 범위 | **도메인 무관.** 어떤 링크든 본문을 읽어 빈소·일시·상주를 추출 |
| 처리 | 서버가 링크를 가져와(SSRF 방어 필수) 본문 추출 → LLM 구조화 |
| 반환 | `{ kind, recipientName, recipientPhone, address, deliverAt, confidence }` — `kind` 는 `"obit"`(부고)·`"wed"`(청첩) |
| 반환 단서 | `kind` 는 포털 1단계의 **경조사 구분과 상품 목록을 바꿉니다**(표시용이 아닙니다). `recipientPhone` 은 배송완료 알림 명단의 **받는분 행**이 쓰는 번호라, 비면 행은 남고 그 수신자에게만 발송이 안 됩니다. `deliverAt` 은 부고에서 **비어 올 수 있습니다**(즉시배송 전제). 프런트의 단일 계약은 `js/data/order-autofill.js` 의 `parseOrderUrl` 입니다(호출부 3곳) — 필드를 늘리거나 줄이면 이 표와 함께 고칠 것 |
| 실패 | 자동 입력 없이 직접 입력으로 계속. **조용히 넘기지 말고 안내** |
| 검수 책임 | 자동 입력된 값도 **주문자가 확인 후 제출**한 것으로 본다. 확인 화면에 "자동 입력됨" 표시 |
| 보안 | 내부망·사설 IP·파일 스킴 차단. 리다이렉트 횟수 제한. 응답 크기 제한 |
| 비용 | 링크당 1회 호출. 같은 링크 재요청은 캐시 |

⚠ **미결**: 정확도 기준(confidence 임계값), 실패율 모니터링 지표 (→ 10.4 Q5).

### 9.3.2 주문 문자 텍스트 인식

거래처가 **카카오톡·문자로 보낸 평문 주문서**를 읽습니다. 링크가 아닙니다 —
실제 표본은 세 갈래입니다: **부고 통보형**(장례식장 주소 + 고인 + 조문 명의),
**배송 지시형**(상품·금액 + 일시 + 주소 + 받는분 + 문구 + 명의),
**공문형**(`1. 행사명 / 2. 행사일시 / 3. 행사장소 / 4. 화환문구` 번호 항목).

| 항목 | 내용 |
|---|---|
| 요청 | `{ text, catalog[] }` — 원문 전체와 **주문 가능한 상품명 목록**. 상품은 카탈로그 안에서만 고릅니다(추측 금지 — 청구 근거입니다) |
| 반환 | `{ kind, addr, toName, toPhone, date, time, vague, amount, product, ribbonPhrase, ribbonSender, note, got[] }` |
| `kind` | `"obit"`(근조) · `"congrat"`(축하). 링크 파서의 `kind`(→ 9.3.1)와 **같은 어휘**를 씁니다 |
| `vague` | 날짜는 읽었지만 **시각을 특정하지 못한 표현**(`오전 중`·`시각 미기재`). 시각 칸을 추측으로 채우지 않기 위한 자리이고, 채운 필드가 아니므로 `got[]` 에 들어가지 않습니다 |
| `got[]` | **채운 필드 이름 목록.** 화면 안내 문구("배송지와 받는분을 채웠습니다")가 이걸 읽습니다. 값의 유무로 역산하지 않습니다 — 빈 문자열을 채운 것과 못 읽은 것이 구분돼야 합니다 |
| `note` | **소비하지 않은 원문 전체.** 요청사항 칸으로 들어갑니다 |
| 제1원칙 | **틀린 값보다 빈 칸이 낫다.** 여기서 나온 값이 배송지·배송시각·청구금액이 됩니다. 확신이 서는 모양만 채우고, 후보가 둘이거나 형태가 어긋나면 **비운 채 `note` 로 넘깁니다** |
| 품질 지표 | **'채운 비율'이 아니라 '틀린 값 건수'로 잽니다.** 빈 칸은 담당자가 원문을 보고 1초에 채우지만, 틀린 주소는 화환이 다른 곳에 갑니다 |
| 원문 보존 | 소비하지 않은 줄은 **한 줄도 버리지 않습니다**(불변식) |
| 실패 | 하나도 못 읽으면 다이얼로그를 닫지 않고 그 자리에서 안내. 붙여 넣은 원문은 입력칸에 남습니다 |
| 검수 책임 | 링크와 같습니다 — 자동 입력된 값도 **담당자가 확인 후 저장**한 것으로 봅니다 |
| 호출 화면 | **관리자 등록 모달 둘(B2C·B2B)뿐입니다.** 포털 주문 퍼널(→ 3.2)에는 없습니다 |
| 보안 | 가져올 URL 이 없어 SSRF 면이 없습니다. 대신 **원문에 개인정보가 그대로 들어 있습니다**(받는분 이름·연락처·빈소) — 프롬프트 로그 보관 기간과 마스킹 정책이 필요합니다 |

**현재 상태 — 규칙 기반 데모 파서입니다.** 프런트의 단일 계약은
`js/data/order-text.js` 의 `parseOrderText` + `applyOrderText` 이고, 지금은 서버 없이
정규식·어휘 사전으로 읽습니다. **실 API 가 붙으면 `parseOrderText` 내부만 갈아끼웁니다**
— 호출부(등록 모달 둘)는 위 반환 계약만 압니다. 링크 파서(`order-autofill.js`)와는
**다른 모듈**이며 한쪽을 다른 쪽으로 대신할 수 없습니다.

⚠ **API 로 바꿔도 회귀 코퍼스는 그대로 씁니다** — `tools/test-order-text.mjs`
(**39케이스**, 실패 시 exit 1). 아래는 실측에서 실제로 나온 오판이고 LLM 도 같은
함정에 빠집니다. **채우는 비율이 올라가도 이 39건에서 틀린 값이 하나라도 생기면 후퇴입니다.**

| 실측 오판 | 올바른 동작 |
|---|---|
| 계좌번호 `302-0123-4567` → 연락처 `02-0123-4567` | 국번·경계 검사로 거부 |
| 전화번호 `02-3010-2230` → 배송일 `2027-02-30` | 달력 검증(2월 30일은 없다) |
| `발인 : 9월 18일 07:00` → 배송일시 | 발인·별세는 **배송일시가 아니다** |
| `저녁 7시` → `07:00` | 오전/아침/새벽 · 오후/저녁/밤 · 낮/정오/자정 구분 |
| `17만 5000원` → `5,000원` | 복합 표기(`3만5천원` 포함)까지 읽는다 |
| `2.5만원` → 2월 5일 | 뒤에 단위가 붙으면 날짜가 아니다 |
| 장례식장 이름·부고 안내문 → 리본문구 | 문구는 **정형 어미**를 가진 줄만 |
| `故 한성규 부친상` → 이름 `故 부친상` | 이름은 **양쪽 앵커**로 판정 |
| 빈소 `특2호실` 이 도로명 주소를 이김 | 도로명이 있는 값이 배송지 |
| 한 줄 카톡 문자 140자 전체 → 배송지 | 괄호 밖 쉼표·하이픈으로 조각내 읽는다 |

  빠지는 셈이라 법무 검토가 필요합니다.

**템플릿 초안 (2026-09-17 채택 · 카카오 검수 전, 변수는 `#{}`)**

동의 마감 임박:

```
[올해의경조사] #{귀속월} 거래명세서 동의 마감 안내
#{회사명} 담당자님, #{귀속월} 귀속 거래명세서(#{건수}건 · #{금액}원)의
계산서 발급 동의 마감이 #{마감일시}입니다.
마감까지 동의가 없으면 그 시각에 자동으로 동의 처리되어 계산서가 발급됩니다.
▶ 명세서 확인·동의: 거래처 포털 > 거래명세서 조회
```

자동 동의 처리:

```
[올해의경조사] #{귀속월} 계산서 발급 안내
#{마감일시}까지 의사표시가 없어 #{귀속월} 귀속 거래명세서(#{금액}원)가
약관에 따라 자동 동의 처리되었고, 계산서(작성일자 #{작성일자})가 발급되었습니다.
정산기한은 #{정산기한}입니다.
▶ 명세서 보기: 거래처 포털 > 거래명세서 조회
```

링크는 공개 열람 링크가 아니라 **포털**입니다 — 동의는 로그인해야 할 수 있고, 공개 링크는 문서만 보여 줍니다.
- 발송 실패(수신거부·번호오류)는 로그로 남기고 관리자 화면에 표시합니다.

## 10.5 용어집

| 용어 | 뜻 |
|---|---|
| 거래처 | 제휴 기업. 월 후불로 정산하는 B2B 고객 |
| 부서 분리 | 같은 사업자번호로 여러 거래처 레코드를 두는 것. 정상 시나리오 |
| 귀속월 | 그 주문이 포함되는 정산 대상 월 |
| 발급일 | 거래명세서가 나가는 날(10:00). 거래처별 `invoiceDay`. 계산서는 동의 즉시 발급된다 |
| 정산 기한 | 발급일이 속한 달의 말일 |
| 동의 마감 | 계산서 발급 동의를 받는 기한. 발급월 10일 13:00(발급일 1~10) / 28일 13:00(11~28) |
| 자동 동의 | 마감까지 동의가 없을 때 마감 시각에 동의로 처리하는 것. `agreed_mode=auto` |
| 작성일자 | 계산서에 찍히는 날짜. 1~10 그룹 = 귀속월 말일, 11~28 그룹 = 동의한 날 |
| 계산서(면세) | 전 품목 면세라 세금계산서 대신 발급하는 문서. 바로빌 API |
| 거래 조건 | 구 '거래처 참고사항'. 그 거래처에만 적용되는 상품·금액·절차 규칙 |
| 반입 제한 | 특정 지역·장례식장에서 허용되는 상품이 한정되는 것 |
| capability URL | 링크를 아는 것이 곧 권한인 URL. 공개 명세서 링크 |
